## 정렬 기준

`AGENTS.md`는 우선순위를 "심각도 단독이 아니라 **유예 비용 대 수정 공수**"로 정하라고 한다.
그래서 심각도(P0/P1) 순이 아니라 아래 축으로 정렬했다.

| 등급 | 뜻 |
|---|---|
| **폐기(discard)** | 지금 안 고치면 그 위에 쌓은 후속 구현을 **버리고 다시 만들어야** 한다 |
| **재작업(rework)** | 후속 구현은 살아남고 배선·정리만 다시 한다 |
| **지연(delay)** | 기능은 멀쩡하고 일정만 밀린다 |

같은 등급 안에서는 **수정 공수가 작은 것을 위**에 뒀다(같은 값이면 싼 것부터 닫는 게 이득이다).

**열린 A는 없다.** 아래는 전부 B/C이며, A는 발견 즉시 해당 task 안에서 닫는다.

## 1군 — 폐기급 (지금 안 닫으면 후속 작업을 버리게 된다)

### ① `B-10` — 타입 있는 edit 가능 실행 집행이 없다

- **미수정 비용: 폐기.** M9(Development Pipeline)는 edit 가능 worker가 전제인데, 집행 없이 쓰기를
  켜면 산출물이 "승인 문서가 장식인 상태"에서 생산된다. 사후에 그 산출물을 신뢰할 방법이 없어
  **다시 만들어야** 한다.
- **가장 큰 문제는 심각도가 아니라 소유자 부재다.** trigger는 "M5c에서 Claude 쓰기 실행을 켜기 전"인데
  M5c 잔여 범위(supervisor · trusted Git · autopilot CLI)에도, M6~M8에도 이 기능이 없다 →
  **어느 마일스톤의 자재 목록에도 없이 M9 압박 속에서 즉석 발명될 것이다.**
- **조치**: M6 또는 신설 M6.5에 **소유 마일스톤을 지정**한다. 이건 코드 작업 전에 계획에서 끝난다.
- 기한(대장): M5c에서 쓰기 실행 켜기 전 — **하드 게이트**

### ② ~~`B-F1`~~ — **closed (2026-08-04, Task 3C)**

- 폐기급이었고 그래서 첫 spawn과 **같은 커밋에서** 닫았다. 독립 리뷰가 요건 ①~④ 집행과
  중복 spawn 경로 부재를 실제 실행으로 확인했다. 잔여 한계는 아래 `B-18`이다.

### ②-a `B-18` — `cleanupConfirmed`가 `setsid()` 탈출 자손을 못 본다 *(신규)*

- **미수정 비용: 재작업 + 오탐.** 그룹을 탈출한 자손이 있으면 `kill(-pgid,0)`이 ESRCH를 돌려주고
  kernel이 **성공 영수증**을 발행하는데 고아는 살아 있다 — `cleanupConfirmed: true` + 살아 있는 고아.
- **지금 확률은 낮다**(digest 승인된 node+entrypoint만 실행). **daemonize하는 entrypoint를 승인하면
  확실히 발현한다.** `managedProcess.ts` 헤더의 "모든 자손"은 과장이며 정정 대상.
- 기한: daemonize 가능한 실제 controller entrypoint 승인 전 / live runner 배선 전
  (`B-13`·`C-18`과 같은 발화점)

### ③ `B-12` — 재시작하면 토큰·경과 회계가 0으로 초기화된다

- **미수정 비용: 재작업이지만 M6의 완료 조건을 무효화한다.** 대장 기한은 "늦어도 M5c"이나,
  **실질 기한은 M6 입장 게이트**다 — M6의 fresh-context rotation이 곧 restart이고, 재시작마다
  예산이 새로 생기면 M6 완료 조건("Coordinator 교체 전후 동일")을 **측정할 수 없다.**
  조건을 검증 못 하는 채로 M6를 통과시키면 그 승인 자체가 무의미해진다.
- **조치**: 대장의 기한 표기를 "늦어도 M5c"에서 **"M6 rotation 착수 전(하드)"** 로 함께 명시한다.
- 현재: `tokensUsed`/`startedAtMs`가 controller in-memory. kernel의 durable
  `budget_elapsed_exhausted`는 커밋 시점에 별도로 걸리므로 표면이 늘지는 않았다.

## 2군 — 재작업급 · 지금이 가장 쌀 때

### ④ `B-13` — durable 완료가 정리 확인보다 먼저이고 `stop` 실패는 삼켜진다

- **상태 변화 주의**: 이 항목은 "지금 프로세스를 띄우지 않으므로 관측되는 위험 없음"으로 유예됐다.
  **Task 3C가 실제 spawn을 도입했으므로 그 전제가 소멸했다.**
- **미수정 비용: 재작업 + 오탐.** 프로세스가 실제로 죽지 않아도 durable state는 "끝났다"가 되고
  정리 실패가 marker로 남지 않는다 → 좌초 프로세스가 다음 batch의 자원을 먹고, 사후에
  "정리됐다"는 기록만 남아 원인 추적이 불가능해진다.
- **조치**: Task 3C 리뷰에 **재분류 판정을 명시 요청했다.** 리뷰가 "3C가 닫았다"로 판정하면 closed,
  아니면 **A로 승격 후보**다(실제 프로세스 누수는 A 정의에 해당).
- 기한(대장): live runner 착수 전 또는 프로세스를 띄우는 provider 배선 시 — **이미 발화했다**

### ⑤ `B-9` — codex JSONL payload 필드명·semantics를 live로 확인하지 않았다

- **미수정 비용: 재작업(fixture 연쇄).** M5a 5차 + M5b 7차 + M5c 3A 6차 = **약 18회 리비전이 전부
  가짜 CLI fixture 상대로** 검증됐다. 실제 필드명이 다르면 그 fixture 전부를 갱신해야 한다.
  파서는 fail-closed라 **성공으로 오인되지는 않는다** — 그래서 폐기가 아니라 재작업이다.
- **수정 공수: 소.** 대장 자체 평가가 "live 1회 캡처 + fixture 갱신"이다.
- **비용 대비 공수가 이 목록에서 가장 유리하다.** 리뷰어 권고도 이걸 1순위로 앞당기라는 것.
- 기한(대장): 첫 live 실행 착수 전 — **하드 게이트**

### ⑥ `B-7` — live 인증 방식 미정 + secret redaction 미해결

- **미수정 비용: 지연.** 기능 손상은 없고 live를 못 켠다.
- **수정 공수: ⓐ 인증 방식은 사람이 고르기만 하면 되고 코드 위험이 0이다.**
  ⓑ redaction은 별도 작업.
- **이 목록에서 가장 싼 항목.** 지금 결정만 해두면 최종 handoff의 분산이 줄어든다.
- 기한(대장): 첫 live 실행 착수 전 — **하드 게이트**

### ⑥-a `B-19` — run 전역 프로세스 상한이 `maxTasksPerRun` 상수를 빌려 쓴다 *(신규)*

- **미수정 비용: 재작업(조용한 변경).** 로드맵의 32는 **run당 task** 수인데 도달 가능한 검사는
  **run당 프로세스** 수를 센다. 지금은 두 값이 같아 동작이 방어 가능하나, task fan-out 때문에
  `maxTasksPerRun`을 조정하면 **프로세스 상한이 소리 없이 따라 움직인다.**
- **수정 공수: 소**(전용 상수 분리 + 로드맵 문구 정정).
- 기한: 그 상수를 바꾸기 전, 늦어도 M6 spawn 계층 착수 전

### ⑦ `B-16` — 안전한 typed-write publication 경로가 없다

- **미수정 비용: 재작업.** 첫 real typed-write 산출물을 배선하는 순간 필요하다.
- **현재 fail closed**(발행·교체 거부, 생성 syscall 0)라 지금은 무해하다. Task 3C도 열지 않았다.
- 기한(대장): 첫 real typed-write 산출물 배선 전, 늦어도 M5c 통합
