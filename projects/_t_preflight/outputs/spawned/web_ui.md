## XSS 방어 계약 (search_api에 요청할 변경)

**이 페이지는 `innerHTML`을 한 번도 쓰지 않는다.** 이게 유일한 방어선이고, 나머지는 전부 이 한 줄에서 파생된다.

현재 계약은 서버가 `"...<mark>일치</mark>..."` 문자열을 준다. 그러면 클라이언트는 그 문자열을 `innerHTML`로 넣을 수밖에 없고, 사내 문서 전체의 XSS 안전성이 **서버의 이스케이프-후-삽입 순서 한 곳**에 걸린다. 색인 대상 폴더에 파일을 넣을 수 있는 사람 = SSO 뒤 전 직원을 상대로 저장형 XSS를 심을 수 있는 사람이 된다.

교체 계약 (양쪽 합쳐 5줄):

- 서버: FTS5 `snippet()`의 마커 인자를 `<mark>`/`</mark>` 대신 제어문자 `char(2)`/`char(3)`으로 준다. 이스케이프 로직 자체가 사라진다.
- 클라이언트: `snippet.split(/[\u0002\u0003]/)`로 자르고 홀짝으로 `document.createElement('mark')` / `document.createTextNode()`. 전부 `textContent`.
- indexer: 본문 추출 시 제어문자(`\u0000-\u0008` 등)를 제거한다. 이미 NFC 정규화를 하기로 했으므로 같은 자리에 한 줄.

핵심은 "더 안전한 이스케이프"가 아니라 **실패 등급을 낮추는 것**이다. 제어문자가 어쩌다 본문에 남아 있어도 최악의 결과는 `스크립트 실행`이 아니라 `엉뚱한 곳이 굵게 표시됨`이다.

`title`은 `textContent`. `url`은 `href`에 넣기 전에 `new URL(u)`로 파싱해 `http:`/`https:`가 아니면 링크 대신 평문으로 렌더한다 (문서 링크 접두사나 파일명에서 `javascript:`가 들어오는 경로를 막는다).

## Risks

### Critical

- **스니펫 저장형 XSS** — 4번 결정이 반영되지 않고 서버가 보낸 HTML 문자열을 `innerHTML`로 렌더하면, 색인 대상 폴더에 파일을 넣을 수 있는 사람이 SSO 뒤 전 직원의 브라우저에서 스크립트를 실행시킬 수 있다. 사내망·인증 뒤라는 사실이 완화 요인이 아니라 오히려 피해 표면(사내 시스템 세션)을 키운다. 완화: 제어문자 구분자 계약 + 페이지 전역 `innerHTML` 금지. 이 결정이 확정되기 전에는 결과 렌더 코드를 쓰지 않는다.

### High

- **`href` 스킴 주입** — 문서 링크 접두사(`link_prefix`)나 파일명에서 `javascript:`·`data:` URL이 들어오면 클릭 한 번에 같은 사고가 난다. 스니펫만 막고 끝내기 쉬운 지점이다. 완화: `new URL()` 프로토콜 검사, 실패 시 평문.
- **SSO 세션 만료의 오진** — 프록시가 로그인 페이지를 200 HTML로 돌려주면 JSON 파싱이 깨진다. 이걸 일반 에러 문구로 뭉개면 사용자는 "검색이 고장 났다"고 판단하고 신고하거나 이탈한다. 실제로는 새로고침 한 번이면 된다. 완화: 401 + JSON 파싱 실패를 같은 "세션 만료" 문구로 묶는다.

### Medium

- **debounce가 품질 지표를 오염시킨다** — 6번 결정이 뒤집혀 debounce가 들어가면 `search_log`의 `hit_count=0` 목록이 타이핑 중간 문자열로 채워지고, 시맨틱 검색 도입 여부를 판단할 근거가 사라진다. 로그를 사후에 정제하려 해도 "진짜 실패 질의"와 "접두사"를 구분할 방법이 없다.
- **empty와 error의 사용자 인지 혼동** — 문구를 구분해도, 화면이 둘 다 "결과 없음"처럼 보이면 신고가 한 종류로 뭉쳐 들어온다. 완화: empty는 검색어를 따옴표로 되돌려주고 재시도를 유도하는 문구, error는 원인별 조치 문구로 확실히 다르게 쓴다.
