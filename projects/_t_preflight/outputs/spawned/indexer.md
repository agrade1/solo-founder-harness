## Main Judgment

**PDF 커넥터 단독으로 착수 가능하며, 재색인 CLI는 "임시 테이블에 전부 쓰고 마지막에 한 번 교체"하는 단일 트랜잭션 방식으로 만들어야 한다** — 전체 재색인은 정의상 기존 색인을 지우는 작업이고, 중간에 죽으면 색인이 반쯤 비는데 야간 cron이라 아침까지 아무도 모른다. 이게 내 범위에서 가장 비용 대비 효과가 큰 결정이며, 나머지(추출·로깅)는 계획대로 얇게 만들면 된다.

## Key Findings

- **전체 재색인의 진짜 실패 모드는 "느림"이 아니라 "부분 색인"이다.** `DELETE FROM documents` 후 순차 삽입 도중 PDF 하나가 프로세스를 멈추거나 디스크가 차면, 검색은 계속 동작하면서 문서 절반이 사라진 상태가 된다. `/healthz`의 `last_indexed_at`도 갱신 안 됐을 뿐이지 검색 자체는 200을 반환하므로 조용한 실패다. 트랜잭션 하나로 감싸는 것은 코드 3줄이고, 이 실패 모드를 통째로 없앤다.
- **`pdftotext`는 실패 유형이 두 가지이고 다르게 다뤄야 한다.** ① 종료 코드 비0(암호 걸림·손상) → 그 파일만 건너뛰고 로그, ② 종료 코드 0인데 출력이 거의 빈 문자열(스캔 이미지 PDF) → 색인은 하되 경고. ②가 계획의 "조용한 누락"에 해당하고, 종료 코드만 보는 구현은 이걸 놓친다.
- **`pdftotext`가 걸려 멈추는 경우가 있다** (거대·기형 PDF). 타임아웃 없이 서브프로세스를 부르면 야간 배치가 파일 하나 때문에 아침까지 멈춘다. 파일당 타임아웃 1개(예: 60초)는 서브프로세스 방식을 선택한 이유(격리)를 실제로 성립시키는 조건이다.
- **위키 export 커넥터의 어려움은 추출이 아니라 `url` 계산이다.** 텍스트는 마크다운/HTML 그대로 읽으면 되지만, 원문 링크를 만들려면 `link_prefix` + 소스 루트 기준 상대 경로 규칙이 필요하다. 이 규칙이 위키 제품마다 다르고(파일명 그대로 vs slug vs 페이지 ID), **여기가 틀리면 검색 결과가 전부 죽은 링크가 되어 제품이 무용지물이 된다.** 추출 코드보다 이 매핑 확인이 먼저다.
- **제목(`title`) 추출 규칙이 소스마다 갈린다.** PDF는 메타데이터 제목이 비어 있거나 쓰레기값("Microsoft Word - 문서1")인 경우가 흔해 파일명이 더 낫다. 위키는 첫 `# ` 헤딩 또는 front matter가 파일명보다 낫다. 공통 추상화 대상이 아니라 소스별로 다르게 두는 것이 맞다 — 계획의 "인터페이스 나중에" 결정과 같은 방향이다.
- **HTML export는 태그 제거가 필요하다.** 태그를 그대로 색인하면 trigram 토크나이저가 `div`·`class` 문자열까지 색인해 노이즈가 되고 스니펫에 마크업이 튄다. 다만 이건 정규식 몇 줄 수준이고, HTML 파서 의존성을 새로 넣을 이유는 없다.
- **`external_id`를 파일 절대 경로로 두면 안 된다.** 소스 루트를 옮기거나 마운트 경로가 바뀌면 전체가 새 문서로 들어온다. 소스 루트 기준 상대 경로로 고정해야 `(source_id, external_id)` UNIQUE가 의미를 가진다. 전체 재색인 방식이라 upsert 충돌 자체는 드물지만, `url` 안정성과 로그 가독성 때문에도 상대 경로가 맞다.

## Decisions

1. **재색인은 단일 트랜잭션 + 스테이징 후 교체.** `BEGIN` → 임시 테이블(또는 `indexed_at` 세대 마커)에 전량 삽입 → 성공 시 `COMMIT`, 예외 시 `ROLLBACK`. 실패하면 이전 색인이 그대로 남는다. 부분 커밋으로 진행률을 남기는 방식은 기각 — 진행률을 볼 사람이 없는데 부분 색인 리스크만 산다.
2. **파일 단위 실패는 배치를 중단시키지 않는다.** 파일 하나당 try/except로 감싸고 로그에 남기고 계속 간다. 단, **배치 전체의 실패 파일 비율이 임계치(예: 30%)를 넘으면 커밋하지 않고 실패로 끝낸다** — 개별 실패는 정상이지만 대량 실패는 환경 붕괴(poppler 삭제·마운트 해제)이고, 이걸 커밋하면 색인이 텅 빈 채로 검색이 계속 200을 반환한다.
3. **`pdftotext` 호출에 파일당 타임아웃을 둔다.** 타임아웃 초과는 실패 파일로 기록하고 다음 파일로 넘어간다.
4. **추출 실패 로깅은 stdout 사람용 요약 + 기계 판독용 파일 1개.** 종료 시 `총 N개 / 성공 X / 실패 Y / 텍스트부족 Z`를 stdout에 찍고(journald로 감), 실패·경고 파일 목록은 `reindex-report.json` 하나에 쓴다. 관리자에게 목록을 줄 수단이 계획상 필요하고(§리스크 Medium), 로그를 grep하게 만드는 것보다 파일 하나가 싸다. DB 테이블 추가는 기각.
5. **색인기 시작 시 사전 점검 3개를 하고 실패하면 즉시 종료한다.** ① `pdftotext -v` 존재 확인, ② `sources` 각 `root_path` 존재·읽기 가능 확인, ③ allowlist 판정 통과 확인(access_guard 제공 로직 호출). 특히 ②는 마운트 해제 시 "파일 0개 = 정상 완료"로 오인되는 것을 막는다 — **디렉터리가 비어 있는 것과 디렉터리가 없는 것을 구분한다.**
6. **`external_id`는 소스 `root_path` 기준 상대 경로.** `title`은 PDF는 파일명(확장자 제거), 위키는 첫 헤딩 또는 front matter `title`, 없으면 파일명. `updated_at`은 파일 mtime(위키 front matter에 날짜가 있으면 그것 우선).
7. **커넥터 공통 인터페이스는 위키 커넥터(순서 4단계)를 구현하는 시점에 뽑는다.** PDF 단계에서는 함수 하나로 둔다. 상위 계획 결정 7과 동일하며, 내 쪽에서 미리 만들지 않는다.
8. **HTML export는 정규식 태그 제거 + 엔티티 디코드만.** `<script>`/`<style>` 블록 내용은 제거하고 본문만 남긴다. HTML 파서 의존성 추가는 기각(export 파일 구조가 기계 생성이라 단순하다). 마크다운은 문법 기호를 굳이 벗기지 않고 그대로 색인한다 — trigram 검색에서 손실이 거의 없고 스니펫도 읽을 수 있다.
9. **OCR·증분 색인·병렬 추출 전부 미도입.** 병렬화는 재색인이 야간 창을 넘길 때, 증분은 재색인이 30분을 넘길 때(상위 계획 기준), OCR은 도입하지 않는다.

## Handoff Notes

- **search_api와의 경계**: 나는 `documents` 테이블에 쓰기만 하고 `documents_fts`·트리거·조회는 건드리지 않는다. 단 **트리거 기반 동기화가 내 단일 트랜잭션 안에서 동작해야 한다** — search_api가 `content='documents'` external content 방식을 쓰면 대량 삽입 시 트리거 비용이 붙는다. 재색인이 야간 창을 넘기면 이 지점을 함께 재검토할 대상으로 남긴다(지금 최적화하지 않는다).
- **access_guard와의 경계**: allowlist 판정은 access_guard의 함수를 호출한다. 내가 별도 구현하지 않는다 — 판정 로직이 두 개가 되면 불일치가 곧 유출이다. 심볼릭 링크 차단과 실경로 검증은 파일 순회를 하는 내 쪽 책임으로 두되, 판정 기준 자체는 access_guard가 소유한다. 이 소유권 분리가 코드에 명시돼야 한다.
- **의도적으로 만들지 않은 것**: OCR, 증분 색인, 삭제 감지, 병렬 추출, 커넥터 추상 인터페이스, 내용 해시 중복 제거, 인코딩 자동 추측, HTML 파서 의존성, 색인 진행률 UI, 재시도 로직. 도입 트리거는 각각 §Decisions·§Risks에 적었다 — 트리거 없이 되살리지 말 것.
- **되돌려야 하는 조건 2개**: ① `pdftotext` 설치 불가 → 추출 방식은 tech_lead 결정 사항이므로 내가 대체 라이브러리를 고르지 않는다. ② 위키가 API-only → 커넥터 범위가 바뀌므로 상위 계획 §Assumptions 재검토.
- 이 문서는 계측용 프로젝트 `_t_preflight`의 산출물이며, 사업 판단 근거로 사용하지 않는다.
